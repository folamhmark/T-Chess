# Progress Bar Animation Specification

**Версия:** 2.0 · **Дата:** 16 ноября 2026 года.

**Продукт:** T-Chess · **Компонент:** «Путь к призам».

**Эталон реализации:** [`app.js`](app.js), [`styles.css`](styles.css), SVG в [`index.html`](index.html).

**Демо:** [открыть прототип](https://chess-marathon-progress-anim.folamhmark.chatgpt.site) · **Запуск:** [README](README.md).

## 1. Статус и границы документа

Документ описывает визуальные состояния, геометрию и анимацию текущего прототипа, а также требования для подключения компонента к настоящему прогрессу пользователя.

Обозначения:

- **Зафиксировано** — решение из согласованного прототипа; реализуется без изменения визуального поведения.
- **Контракт интеграции** — требование к основному приложению; в автономном HTML-демо нет API, календаря и хранения данных.
- **Открыто** — правило не было определено; его нельзя считать согласованным только на основании этой спецификации.

Все числовые тайминги ниже соответствуют обычной скорости, без режима замедления и без `prefers-reduced-motion`. Единицы геометрии — CSS px; на нативных платформах использовать соответствующие логические единицы, а не физические пиксели дисплея.

## 2. Назначение и правила прогресса

Компонент показывает накопленные активные дни марафона: от 0 до 20. Зачёт нового дня должен давать понятную обратную связь: активируется один новый маркер, меняются число и нижняя подпись; на 10-м дне дополнительно перестраиваются участки точек.

**Зафиксировано:**

1. Активный день можно получить за урок или задачу дня.
2. За одни календарные сутки засчитывается не больше одного активного дня.
3. Солнце соответствует 1-му дню, подарок — 10-му, кубок — 20-му.
4. Визуальное состояние этапа определяется количеством активных дней.
5. Нижняя подпись определяется тем, засчитан ли сегодняшний день. Это отдельный признак.
6. Ореолы, большие анимированные кольца, конфетти и всплывающая плашка приза не используются.
7. Фон — голубой градиент; карта и пингвин отсутствуют.

**Контракт интеграции:** клиент отображает подтверждённый прогресс. Завершение анимации не выдаёт награду и не увеличивает серверный счётчик. Повторный просмотр уже показанного состояния не считается новым зачётом.

Дни накопительные в рамках этого компонента. Механика стрика, сгорания прогресса, продления марафона и восстановления пропусков этим документом не задаётся.

## 3. Модель данных и источник истины

### 3.1. Входной снимок для приложения

Ниже логический контракт, а не существующие имена параметров API:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `activeDays` | integer, 0…20 | Подтверждённый накопленный прогресс. |
| `todayCredited` | boolean | Засчитан ли активный день за текущую календарную дату. |
| `revision` | server-defined comparable value | Версия снимка для защиты от устаревших ответов. |
| `creditEventId` | string / null | Уникальный идентификатор зачёта; нужен для дедупликации анимации. |
| `creditedDate` | date / null | Календарная дата зачёта по правилам сервера. |
| `serverNow`, `dayBoundary` | server-defined | Время и следующая граница суток; не вычислять правила зачёта только из часов устройства. |

`previousActiveDays` и идентификатор уже показанного события хранятся клиентом как контекст отображения. Поля, связанные с наградами, могут существовать в другом сервисе, но не выводятся из цвета иконки.

### 3.2. Ограничения

- Валидный диапазон `activeDays` — целые значения 0…20. Не округлять дробные ответы молча.
- Сочетание `activeDays = 0` и `todayCredited = true` невалидно.
- При `activeDays >= 1` допустимы оба значения `todayCredited`.
- Новый обычный зачёт переводит `N` в `N + 1`, если `N < 20`.
- На значении 20 новый день не создаёт состояние 21 и не активирует дополнительный маркер.
- Не принимать ответ со старой `revision` поверх более нового снимка.
- Дубликат `creditEventId` не должен запускать анимацию ещё раз.

### 3.3. Что реально хранит демо

| Переменная в `app.js` | Значение |
| --- | --- |
| `from`, `to` | Выбранный демонстрационный переход. |
| `current` | Установившееся значение; при анимации обновляется в конце. |
| `credited` | Зачёт дня в выбранном демонстрационном сценарии. |
| `busy` | Выполняется ли анимация зачёта. |
| `run` | Счётчик отмен, исключающий завершение устаревшей анимации. |
| `views[]` | Текущие видимые `x`, `size`, `opacity`, `fill`, `scale` каждого маркера. |

Демо не сохраняет эти значения между загрузками. Начальный сценарий — 2→3, начальный прогресс — 2, сегодняшний день не засчитан.

## 5. Раскладка и группировка

### 5.1. Режим A: 0–9 активных дней

Порядок слева направо:

`Солнце — 8 обычных точек дней 2–9 — Подарок — группа из 3 маленьких точек — Кубок`

- Солнце активно при `N >= 1`.
- Обычная точка дня `d` синяя при `d <= N`.
- Подарок и кубок неактивны.
- Три маленькие точки после подарка серые и условно обозначают весь будущий участок 11–19.

### 5.2. Режим B: 10–20 активных дней

Порядок слева направо:

`Солнце — группа из 3 маленьких точек — Подарок — 9 обычных точек дней 11–19 — Кубок`

- Солнце и подарок активны.
- Три маленькие точки перед подарком синие: первый участок уже пройден.
- Обычная точка дня `d` синяя при `d <= N`.
- Кубок активен только при `N = 20`.
- На 20 днях второй участок остаётся раскрытым: 9 синих обычных точек. Дополнительного схлопывания при завершении нет.

### 5.3. Расчёт промежутков

Компактная группа участвует в распределении ширины как **один элемент 20 px**. Внутренние зазоры всегда 4 px.

```text
W = ширина ряда
S = суммарная ширина иконок, обычных точек и компактной группы
K = число элементов, где компактная группа считается одним элементом
G = (W − S) / (K − 1)
```

| Режим | Состав S | K | G при W = 303 |
| --- | --- | --- | --- |
| A | 3 × 32 + 8 × 8 + 20 = 180 | 12 | 123 / 11 ≈ 11,182 |
| B | 3 × 32 + 9 × 8 + 20 = 188 | 13 | 115 / 12 ≈ 9,583 |

Первая и последняя иконки касаются границ ряда своими контейнерами: центр солнца x = 16, центр кубка x = W − 16. Не округлять каждый зазор отдельно до целых пикселей: это накопит ошибку к правому краю.

### 5.4. Что происходит с отдельными точками при схлопывании

Для сохранения непрерывности код держит 20 логических узлов, но лишние визуальные узлы получают нулевую прозрачность.

- Первый участок: три видимых представителя — дни **2, 5, 9**; прочие точки участка съезжаются к ближайшему представителю и исчезают.
- Второй участок в компактном виде: представители — дни **11, 15, 19**; при раскрытии все девять точек занимают свои позиции и появляются.
- При равном расстоянии выбирается более ранний представитель, как в `layout()`.
- Представители — технический приём анимации, не отдельные заработанные или пропущенные дни. Пользователь видит обозначение целого участка.

## 7. Состояние сегодняшнего дня

| ID | Условие | Нижняя подпись | Цвет | Анимация при открытии |
| --- | --- | --- | --- | --- |
| `day/not-credited` | `todayCredited = false` | «Сегодняшний день не засчитан» | `#343638` | Нет |
| `day/crediting` | Подтверждён новый зачёт и идёт визуальный переход | Старая подпись сменяется новой в момент t = 430 мс | Старый цвет → `#428BF9` при замене текста | По таймлайну |
| `day/credited` | `todayCredited = true` | «Сегодняшний день засчитан» | `#428BF9` | Нет, если это уже показанный снимок |

Пример: 3 накопленных дня и сегодняшний день не засчитан — две синие обычные точки, активное солнце, тёмная нижняя подпись. После нового зачёта получается 4 дня и синяя подпись.

При смене календарной даты накопленные точки и иконки не сбрасываются. Если сервер возвращает `todayCredited = false`, меняется только подпись. Это обновление состояния, а не анимация нового заработанного дня.

На `N = 20` допустимы обе подписи: в день завершения — засчитан; при просмотре в следующий день — не засчитан. Отдельный текст «Марафон завершён» внутри карточки не согласован. Надпись «Все 20 дней засчитаны» существует только в панели демонстрации.

## 8. Реестр операционных состояний

Первые пять состояний ниже поддерживает демо. Сетевые состояния — контракт интеграции, их отдельные макеты в демо отсутствуют.

| Состояние | Вход | Что видит пользователь / доступность | Выход |
| --- | --- | --- | --- |
| `view/ready` | Получен валидный снимок или выбран демо-сценарий | Установившийся ряд и корректная подпись | Новый зачёт, смена снимка, закрытие |
| `view/animating` | Подтверждён новый одиночный зачёт | Единый таймлайн; повторный запуск и замедление заблокированы | Завершение, отмена, reduced motion |
| `view/settled` | Достигнут конец таймлайна | Итоговая раскладка и подпись; в демо доступен повтор | Новый сценарий, сброс, закрытие |
| `view/resetting` | Смена демо-сценария или сброс | Переход к выбранному началу за 440 мс | Готовность или запуск нового перехода |
| `view/help-open` | Нажата кнопка `?` | Подсказка поверх карточки; прогресс не меняется | Повторный тап, клик снаружи, Escape |
| `data/loading` | Нет подтверждённых данных | Не показывать «0 дней» как факт. Нужен loading-вариант контейнера; дизайн открыт | Валидный ответ или ошибка |
| `data/stale` | Есть последний валидный снимок, идёт обновление | Сохранить последний прогресс; не запускать зачёт на основании ожидания | Новый ответ, ошибка обновления |
| `data/error-empty` | Загрузка не удалась, снимка нет | Не выдумывать прогресс и подпись. Ошибка и повтор принадлежат контейнеру; макет открыт | Успешный повтор или выход |
| `data/error-with-snapshot` | Обновление не удалось, снимок есть | Сохранить последний прогресс; ошибка загрузки не окрашивает его как новый успех | Успешный повтор или выход |
| `credit/pending` | Задание завершено, сервер ещё не подтвердил зачёт | Не увеличивать N, не запускать success-motion | Подтверждение, отказ, неопределённый результат |
| `credit/duplicate` | Повторный event ID / зачёт уже есть | Сохранить состояние без повторной анимации и начисления | Готовность |
| `credit/unknown-result` | Таймаут после отправки зачёта | Сначала сверить состояние с сервером; не повторять начисление как новую операцию | Подтверждённый снимок |
| `data/invalid` | N вне диапазона, дробное N, противоречивые поля | Последний валидный снимок либо состояние ошибки без снимка | Валидный снимок |

Приоритеты при конфликте:

1. Применяется только актуальный валидный серверный снимок.
2. Дубликат не запускает новый success-motion.
3. `reducedMotion` определяет способ перехода, но не отменяет подтверждённый результат.
4. Закрытие экрана отменяет только визуальную работу, а не подтверждённый зачёт.
5. Открытая подсказка не замораживает модель прогресса.

## 9. Правила запуска и выбор перехода

### 9.1. Контракт интеграции

| Ситуация | Поведение |
| --- | --- |
| Первый показ экрана с подтверждённым N | Показать конечное состояние без проигрывания всей истории 0→N. |
| Новый подтверждённый зачёт `N → N+1`, событие ещё не показано | Воспроизвести соответствующую анимацию один раз. |
| Тот же снимок / дубликат события | Ничего не проигрывать повторно. |
| При синхронизации пришёл скачок на несколько дней | Показать актуальное состояние без очереди праздничных анимаций. Это правило интеграции; массовый переход в демо не реализован. |
| Сервер исправил прогресс вниз | Применить подтверждённый снимок без анимации награждения; коррекция не является новым зачётом. |
| Вернулся только новый `todayCredited`, N не изменился | Обновить подпись, не активировать ещё одну точку. |
| Пользователь открыл экран после завершения зачёта на другом экране | Показать актуальный снимок. Автовоспроизведение старого события отдельно не включать. |

### 9.2. Классы одиночных переходов

| Переходы | Акцент | Раскладка | Полная длительность |
| --- | --- | --- | --- |
| 0→1 | Солнце | A→A | **1180 мс** |
| 1→2, 2→3, …, 8→9 | Следующая обычная точка | A→A | **1000 мс** |
| 9→10 | Подарок | **A→B**, схлопывание и раскрытие | **1180 мс** |
| 10→11, 11→12, …, 18→19 | Следующая обычная точка | B→B | **1000 мс** |
| 19→20 | Кубок | B→B | **1180 мс** |

В демо кнопками доступны только 0→1, 2→3, 9→10, 10→11, 19→20. Остальные строки статической матрицы и переходы задаются теми же правилами, но не имеют отдельных кнопок стенда.

## 10. Общая временная шкала

`t = 0` — момент запуска визуального перехода после подтверждения зачёта. Это не момент завершения урока и не начало сетевого запроса.

| Канал | До начала | Интервал | Результат |
| --- | --- | --- | --- |
| Сжатие нового маркера | Масштаб 1 | **0–150 мс** | Масштаб 0,9 |
| Возврат нового маркера | Масштаб 0,9 | **150–800 мс** | Масштаб 1, без overshoot |
| Цвет новой точки / иконки | Старый цвет | **150–800 мс** | Активные цвета |
| Видимость рисунков подарка | Старый вариант | **150–800 мс** | Активный рисунок вместо неактивного |
| Уход числа и нижней подписи | opacity 1, y = 0 | **150–430 мс** | opacity 0; число y = −5, подпись y = −2 |
| Замена текста | Старое число и подпись | **t = 430 мс** | Новое число, «Сегодняшний день засчитан», синий цвет |
| Вход числа и нижней подписи | opacity 0; число y = +5, подпись y = +2 | **430–710 мс** | opacity 1, y = 0 |
| Изменение раскладки, размеров и opacity точек | Видимая исходная геометрия | **210–950 мс** | Конечная геометрия |
| Удержание конечного вида, обычный день | Все каналы завершены | **950–1000 мс** | Готовность в 1000 мс |
| Удержание конечного вида, этап | Все каналы завершены | **950–1180 мс** | Готовность в 1180 мс |

Для переходов без перестройки канал геометрии не вызывает искусственного перемещения: если исходная и целевая позиции совпадают, маркер остаётся на месте.

### 10.1. Контрольные моменты

| t | Ожидаемое состояние |
| --- | --- |
| 0 | Исходный кадр; положение, цвет и текст не перескакивают. |
| 150 | Новый маркер сжат до 90%; начинает возвращаться и окрашиваться. |
| 210 | Начинается перестройка геометрии; на 9→10 появляются первые изменения рядов. |
| 430 | Смена числа и подписи при нулевой opacity. |
| 710 | Новое число и синяя подпись полностью видимы, y = 0. |
| 800 | Новый маркер имеет конечный размер и активные цвета. |
| 950 | Геометрия соответствует выбранному конечному режиму. |
| 1000 / 1180 | Снимается `busy`, фиксируется `current`, обновляется доступное числовое значение. |

Из-за частоты кадров замена текста происходит на первом отрисованном кадре с `t >= 430`. Не требуется физический кадр ровно в 430 мс. Конечные значения фиксируются точно независимо от числа пропущенных промежуточных кадров.

### 10.2. Поведение каждой группы объектов

- **Новый маркер:** scale 1→0,9→1, цвет плавно меняется на активный. На иконках сжимается весь контейнер 32 × 32 вместе с символом.
- **Уже активные маркеры:** повторно не пульсируют и не проигрывают получение. На 9→10 могут перемещаться из-за перестройки.
- **Будущие обычные точки:** остаются серыми. При раскрытии меняют размер, позицию и прозрачность, но не получают ложного синего состояния.
- **Скрываемые точки:** одновременно смещаются к представителям, уменьшаются 8→4 и исчезают 1→0.
- **Представители первой группы:** уменьшаются 8→4, сохраняют opacity 1 и синий цвет.
- **Раскрываемые точки второй группы:** увеличиваются 4→8, разъезжаются к обычным позициям; скрытые появляются 0→1.
- **Иконки этапов:** сохраняют внешнюю геометрию 32 × 32, кроме краткого scale нового этапа; их центры могут сдвигаться с раскладкой.
- **Счётчик:** движется только число N; остальная фраза не меняется и не мигает.
- **Нижняя подпись:** текст и цвет заменяются в невидимой фазе, после чего появляется целевая подпись.

## 11. Формулы анимации для переноса на другую платформу

Anime.js ведёт единый линейный clock. Плавность задаётся функциями ниже, а не отдельным default-easing библиотеки. Не применять easing повторно поверх уже вычисленного прогресса.

```text
clamp(x) = min(1, max(0, x))
lerp(a, b, p) = a + (b − a) × p
S(u) = u² × (3 − 2u), где u = clamp(u)
D(u) = [1 − (1 + 8u) × exp(−8u)] / [1 − 9 × exp(−8)], где u = clamp(u)

fillProgress(t) = D((t − 150) / 650)
layoutProgress(t) = D((t − 210) / 740)
textProgress(t) = S((t − 150) / 560)
```

Масштаб нового маркера:

```text
если t < 150:
    scale = lerp(1, 0.9, S(t / 150))
иначе:
    scale = lerp(0.9, 1, fillProgress(t))
```

Геометрия и видимость:

```text
x = lerp(source.x, target.x, layoutProgress)
size = lerp(source.size, target.size, layoutProgress)
opacity = lerp(source.opacity, target.opacity, layoutProgress)
```

`source` — фактически видимое состояние в момент запуска, не начальная точка старой анимации. Другие маркеры, если прерваны во время сжатия, возвращают свой scale к 1 за 400 мс через D; это предотвращает застревание в уменьшенном состоянии.

Цвета линейно смешиваются по RGB-каналам с `fillProgress`; каждый канал округляется до целого 0…255. У обычной точки исходный неактивный RGB = (237, 237, 238), целевой = (66, 139, 249). У фона иконки исходный = (255, 255, 255); у символа = (151, 157, 167), целевой = белый.

`--inactive-art = 1 − fill`, `--active-art = fill`. Это crossfade двух рисунков подарка и серого/голубого центра солнца. Вырез звезды кубка всегда имеет текущий цвет фона его круга.

Текст при `q = textProgress(t)`:

```text
если q < 0.5:
    текст = исходный
    opacity = 1 − 2q
    число.y = −10q
    подпись.y = −4q
иначе:
    текст = целевой
    p = 2 × (q − 0.5)
    opacity = p
    число.y = 5 × (1 − p)
    подпись.y = 2 × (1 − p)
```

Никакой бесконечной анимации ожидания и автоматического loop у прогресс-бара нет.

## 12. Разбор ключевых переходов

### 12.1. 0→1 — первый активный день

**До:** все иконки серые, восемь обычных точек серые, будущий участок свёрнут в три серые точки, счётчик 0.

**Триггер:** подтверждён первый активный день. **Акцент:** солнце. **Длительность:** 1180 мс.

Солнце сжимается и возвращается; фон становится синим, лучи белыми, центр голубым. На 430 мс меняются число 0→1 и нижняя подпись. Группировка участков и позиции не меняются. Подарок и кубок остаются неактивными.

### 12.2. Обычный день до первого приза — пример 2→3

**До:** солнце активно, точка дня 2 синяя, остальные будущие маркеры серые. **Акцент:** точка дня 3. **Длительность:** 1000 мс.

Меняется следующая точка, число и подпись. Солнце и точка дня 2 повторно не пульсируют. Группа после подарка остаётся из трёх серых точек по 4 px с промежутками 4 px. Конечный размер новой обычной точки — 8 × 8.

### 12.3. 9→10 — первый приз и смена раскладки

**До:** солнце и восемь точек первого участка активны; подарок неактивен; второй участок свёрнут и серый.

**Акцент:** подарок. **Длительность:** 1180 мс.

1. С 0 мс подарок сжимается до 90%; с 150 мс возвращается и окрашивается.
2. С 210 мс дни 2–9 собираются в три синих маленьких представителя; дополнительные точки исчезают.
3. Одновременно участок 11–19 раскрывается в девять серых точек по 8 px.
4. Точки-представители получают точные внутренние промежутки 4 px; общая группа занимает 20 px.
5. Подарок и остальные элементы смещаются в новые позиции единого ряда. Солнце и кубок сохраняют крайние центры.
6. На 430 мс число становится 10, нижняя подпись заменяется засчитанной.
7. К 950 мс раскладка B установлена; в 1180 мс заканчивается операция отображения.

Синяя иконка означает достижение этапа. Она не доказывает, что физический/цифровой приз уже выдан. Всплывающая плашка и переход на экран призов не запускаются.

### 12.4. 10→11 — первый день после подарка

**До:** первая группа свёрнута и синяя; подарок активен; девять точек второго участка серые.

**Акцент:** первая обычная точка после подарка, день 11. **Длительность:** 1000 мс.

Активируется только день 11. Группы не перестраиваются, подарок не проигрывает повторное получение. Число меняется 10→11, нижняя подпись становится синей.

### 12.5. 19→20 — завершение

**До:** солнце, подарок, первая компактная группа и девять обычных точек второго участка синие; кубок серый.

**Акцент:** кубок. **Длительность:** 1180 мс.

Кубок сжимается, возвращается и становится белым на синем круге. Счётчик меняется 19→20. Вторая группа остаётся раскрытой. Нет автоматического закрытия карточки, конфетти, ореола или всплывающей плашки.

## 13. Прерывание, повтор и восстановление

| Событие | Требование / текущее поведение |
| --- | --- |
| Повторный запуск во время зачёта | Игнорируется `busy`; второй таймлайн не создаётся. |
| Нажатие урока во время зачёта | Не создаёт второй зачёт; действует та же блокировка. |
| Сброс во время анимации | Старые анимации остановлены; счётчик `run` изменён; старый callback не может применить результат. |
| Выбран другой демо-сценарий | Переход к новому начальному виду за 440 мс; старый переход отменён. |
| Новый запуск во время 440-мс перестройки | Перестройка отменяется; источник геометрии берётся из видимого промежуточного кадра. |
| Повтор после завершения в демо | Начальное состояние выбранного сценария ставится мгновенно, затем запускается тот же зачёт. Это намеренный инструмент стенда. |
| Закрытие / размонтирование продукта | Контракт интеграции: остановить clock, callbacks и слушатели; подтверждённые данные не откатывать. |
| Возврат после закрытия | Показать актуальный снимок без повторного награждения за уже показанное событие. |
| Приложение ушло в фон | Контракт интеграции: при возвращении сверить снимок; показать итог, если событие уже завершилось. Не растягивать старую анимацию на минуты. |
| Устройство изменило ориентацию | Пересчитать конечную раскладку по новой доступной ширине; не добавлять активных дней. |

В демо resize обрабатывается в установившемся состоянии. Живая переразметка при изменении ширины посреди анимации отдельно не реализована; для основной реализации конечный кадр должен пересчитываться по актуальному W.

При 440-мс сбросе геометрия и цвета интерполируются с `cubic-bezier(.22, 1, .36, 1)`, а счётчик и подпись ставятся в выбранное начальное состояние сразу. Не путать этот технический демо-сброс с производственным зачётом.

## 14. Уменьшение движения, скорость и доступность

### 14.1. Reduced motion

При `prefers-reduced-motion: reduce`:

- Сразу показать конечные x, размеры, opacity и цвета.
- Сразу установить новое число и подпись.
- Не использовать scale, сдвиг текста и промежуточные кадры перестройки.
- Сохранить правильные 8 px обычные точки, 4 px маленькие точки, 4 px зазоры и 32 px иконки.
- Результат зачёта тот же, что в обычном режиме.

Если reduced motion включён во время зачёта, остановить переход и установить его подтверждённый итог. Если настройка выключена после завершения, анимацию задним числом не запускать.

### 14.2. Замедление стенда

Чекбокс «Замедлить ×3» умножает временную шкалу зачёта на 3: обычный день — **3000 мс**, этап — **3540 мс**. Например, замена текста переносится с 430 на 1290 мс, окончание геометрии — с 950 на 2850 мс.

Во время зачёта чекбокс заблокирован. Смена демо-сценария / reset остаётся 440 мс; это отдельный технический переход. Настройку ×3 не переносить в пользовательский продукт.

### 14.3. Семантика и ввод

- Ряд: `role="progressbar"`, `aria-valuemin="0"`, `aria-valuemax="20"`, `aria-valuenow=N`, название «N из 20 активных дней».
- Скрытые при сворачивании узлы: `aria-hidden="true"`. Три маленькие точки не должны озвучиваться как три earned-day.
- Нижняя подпись: `aria-live="polite"`; не отправлять announcement каждый кадр.
- Итоговое доступное значение счётчика фиксируется один раз в конце перехода; reduced motion — сразу.
- Кнопки доступны с клавиатуры; фокус не переносится вслед за анимацией.
- Статус зачёта выражается не только цветом, но и текстом.
- На нативных платформах маленькая иконка `?` должна иметь увеличенную область нажатия без увеличения рисунка. В демо визуальная кнопка — 22 × 22; production touch-target требует адаптации.

## 15. Подсказка и соседние элементы

Кнопка `?` открывает текст:

> Активный день засчитывается за урок или задачу дня. За сутки можно получить один активный день.

Подсказка изначально скрыта. Открытие / закрытие мгновенное, отдельного motion нет. Она закрывается повторным нажатием `?`, кликом снаружи или Escape. `aria-expanded` синхронизирован с видимостью. Открытие не меняет число дней и не отменяет начавшийся зачёт.

Всплывающая подсказка `?` сохранена; удалена именно поздравительная плашка получения приза. Тестовые короткие сообщения нижней навигации в стенде существуют только как заглушки, скрываются через 2400 мс и не являются частью анимации прогресса.

Карточка, заголовок, кнопка `?`, урок, фон и нижнее меню во время зачёта не подпрыгивают, не меняют размеры и не получают отдельные эффекты. Звук и haptic не реализованы и не являются обязательными параметрами текущей версии.

## 16. Надёжность интеграции и пограничные случаи

Это требования к основному приложению; в демо сетевых операций нет.

| Сценарий | Правило отображения / восстановления |
| --- | --- |
| Один и тот же урок отправлен повторно | Сервер дедуплицирует зачёт; клиент не увеличивает N второй раз. |
| Урок и задача дня выполнены в одни сутки | Не больше одного активного дня; второе выполнение не запускает новый маркер. |
| Ответ сервера пришёл после закрытия экрана | Данные могут обновиться в модели; размонтированная карточка не анимируется. |
| На втором устройстве уже засчитан день | Следующая синхронизация показывает подтверждённый снимок; нельзя получить 2 дня за одну дату. |
| Офлайн-выполнение задания | До подтверждения не показывать гарантированный зачёт; правила допустимости офлайн-зачёта требуют серверного решения. |
| Таймаут запроса | Сверить результат по событию / актуальному снимку; не генерировать новый ID начисления на каждый retry. |
| Обновлён только статус награды | Не активировать дополнительную точку; не переигрывать день. |
| Достигнутый приз ещё обрабатывается | Иконка остаётся отражением порога дней. Статус выдачи показывается в системе призов, если предусмотрен. |
| Часы устройства переведены | Не пересчитывать eligibility по локальным часам. |
| Наступили новые сутки | Серверный N сохраняется; статус сегодняшнего дня может стать false; нет анимации уменьшения прогресса. |
| Приложение завершилось посреди анимации | После запуска загрузить снимок и показать статический итог; анимация не является незавершённым начислением. |
| Неизвестная версия ответа / неполные поля | Не смешивать поля из несовместимых снимков; использовать валидный кеш или состояние ошибки. |

Не задавать произвольный клиентский таймаут начисления в этой спецификации: его определяет контракт API. Отсутствие ответа не равно отказу в зачёте и не равно успеху.

## 17. Аналитика для основного приложения

В текущем демо аналитика отсутствует. Ниже минимальная рекомендуемая схема, не событие на каждый кадр.

| Событие | Момент | Основные параметры |
| --- | --- | --- |
| `marathon_progress_view` | Показан валидный снимок | `active_days`, `today_credited`, `layout_mode` |
| `marathon_day_credit_result` | Система зачёта подтвердила результат | `credit_event_id`, `result`, `previous_days`, `active_days`, `source` |
| `marathon_progress_animation_start` | Визуальный переход действительно запущен | `credit_event_id`, `from`, `to`, `duration_ms`, `reduced_motion` |
| `marathon_progress_animation_end` | Конец или отмена визуального перехода | `credit_event_id`, `outcome: completed/interrupted/skipped`, `reason` |
| `marathon_progress_help_open` | Открыта подсказка | `active_days`, `today_credited` |
| `marathon_progress_sync_error` | Не удалось получить валидный снимок | `error_code`, `has_snapshot`, `revision` |

Начисление должно измеряться по подтверждённому событию системы прогресса, а не по окончанию motion. Дедуплицировать результат по ID события; не выводить количество выданных призов из числа просмотров синего подарка.

## 18. Критерии приёмки

### 18.1. Визуальные и геометрические

| ID | Given / When | Then |
| --- | --- | --- |
| V01 | Установившийся режим A | 8 обычных точек; после подарка ровно 3 маленькие. |
| V02 | Установившийся режим B | Перед подарком ровно 3 маленькие; после — 9 обычных. |
| V03 | Измерены видимые обычные точки | Размер каждой 8 × 8 логических px. |
| V04 | Измерена компактная группа | Точки 4 × 4; промежутки между краями 4; ширина всей группы 20. |
| V05 | Иконка активна / неактивна | В обоих случаях контейнер 32 × 32; меняются цвета и рисунок, а не постоянный размер. |
| V06 | N = 0 | Все иконки неактивны, счётчик 0, подпись незасчитанного дня. |
| V07 | N = 20 | Активны все этапы, первая группа компактная, вторая — 9 синих точек. |
| V08 | N любое, `todayCredited=false` | Подпись тёмная, накопленные синие маркеры сохраняются. |
| V09 | `todayCredited=true` | Подпись точно `#428BF9`; счётчик остаётся цветом основного текста. |
| V10 | Открыт демо-экран | Голубой градиент, нет карты и пингвина. |

### 18.2. Motion

| ID | Given / When | Then |
| --- | --- | --- |
| M01 | 0→1 | Активируется солнце за 1180 мс; остальные будущие маркеры не окрашиваются. |
| M02 | 2→3 | Активируется только день 3 за 1000 мс; уже активные элементы не пульсируют. |
| M03 | 9→10 | За 1180 мс активируется подарок, участок A сворачивается, B раскрывается. |
| M04 | 10→11 | Активируется день 11, раскладка B сохраняется. |
| M05 | 19→20 | Активируется кубок за 1180 мс, поздравительной плашки нет. |
| M06 | Отслеживается scale нового маркера | Минимум 0,9 в 150 мс, максимум не выше 1, итог 1. |
| M07 | Проверяется t = 430 мс | Тексты заменяются в невидимой фазе, без однокадровой вспышки. |
| M08 | Проверяется t >= 710 мс | Новое число и подпись видны полностью, смещение текста нулевое. |
| M09 | Проверяется t >= 950 мс | Позиции, размеры и прозрачность соответствуют конечной раскладке. |
| M10 | Включён ×3 в стенде | Все каналы зачёта замедлены втрое; reset остаётся 440 мс. |
| M11 | Быстро выбран другой сценарий | Старый callback не меняет счётчик после отмены; новый переход берёт текущую геометрию. |
| M12 | На этапе 10 или 20 | Нет внешних анимированных колец, ореолов, конфетти и prize popup. |

Тайминги оценивать с допуском в один реально отрисованный кадр; конечные размеры, количество точек, цвета и значения проверяются без накопленной ошибки. Для выборки start/mid/settle использовать, например, 0, 150, 430, 710, 950 и 1180 мс.

### 18.3. Состояния, ввод и интеграция

| ID | Given / When | Then |
| --- | --- | --- |
| S01 | Повторный запуск во время `busy` | Не создаётся второй зачёт / таймлайн. |
| S02 | Сброс после завершения | Возвращаются исходное число, подпись незасчитанного дня и геометрия. |
| S03 | Открыта подсказка; Escape / клик снаружи | Подсказка закрыта, данные не меняются. |
| S04 | Reduced motion включён до запуска | Итог достигается без scale, сдвига и reflow-motion. |
| S05 | Reduced motion включён посреди запуска | Движение прекращается, установлен подтверждённый итог. |
| S06 | Получен дубликат серверного зачёта | Нет повторной анимации и увеличения N. |
| S07 | Пришёл устаревший ответ | Более новый прогресс не откатывается. |
| S08 | Выполнены урок и задача в одни сутки | Зачтён только один день. |
| S09 | Новые сутки при N = 10 | N и иконки сохраняются, подпись может стать незасчитанной, порог 10 не проигрывается заново. |
| S10 | Перезапуск во время motion | Загрузился и показан подтверждённый итог, начисление не повторилось. |
| S11 | Таймаут / офлайн | Не показан выдуманный успех; есть путь сверки состояния. |
| S12 | N = 20 и новое выполнение | Нет состояния 21 и дополнительной точки. |
| S13 | N = 0, `todayCredited=true` или N вне диапазона | Невалидный снимок не подменяет последнее корректное представление. |
| S14 | Управление только клавиатурой | Доступны элементы ввода, виден фокус, нет его перемещения из-за motion. |
| S15 | Размер / ориентация экрана изменились | Ряд не выходит за контейнер; в конечном кадре компактная группа всё ещё 20 px. |

## 19. Нереализованное и открытые решения

Эта спецификация завершает handoff визуального компонента. Следующие продуктовые решения не следует придумывать на клиенте:

| Вопрос | Почему нужен | Владелец решения |
| --- | --- | --- |
| Какой часовой пояс и календарная граница определяют активный день? | Идемпотентность, новые сутки, путешествия и смена часов устройства | Product + Backend |
| Когда начинается и заканчивается марафон, есть ли период восстановления? | Состояния доступности и поздние события | Product |
| Какие конкретно уроки и задачи считаются выполненными? | Серверная eligibility-проверка | Product + Learning + Backend |
| Допускается ли офлайн-зачёт, и к какой дате он относится? | Не терять результат и не давать двойные дни | Product + Backend |
| Как выдаются и активируются призы, какие бывают отказы? | Синий порог не равен фактической выдаче | Product + Rewards/Backend |
| Что делать с карточкой после окончания марафона? | Текст, видимость и будущая навигация | Product + Design |
| Как выглядят initial loading и ошибка без снимка? | Сейчас есть только валидные демо-состояния | Design + Frontend |
| Какие ответы API, retry и версии поддерживаются? | Совместимость и восстановление после таймаута | Backend + Frontend |

Сроки и конкретные ответственные не заданы. Визуальную анимацию можно реализовывать по разделам 4–15; календарь, сетевые состояния и фактическую выдачу призов подключать после согласования соответствующих контрактов. В текущий код эти новые серверные возможности этим документом не добавлены.
